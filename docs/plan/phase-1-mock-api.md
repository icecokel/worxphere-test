# Phase 1. 지원자 데이터와 mock API

[전체 계획](README.md) · 기준: [요구사항](../requirements.md), [화면 명세](../wireframe.md#7-데이터와-mock-api-계약)

## 목표

화면이 사용할 최소 지원자 데이터와 MSW 조회·단계 저장 API를 만든다. UI 구현 전에 지연, 실패, 저장 성공, 새로고침 유지 규칙을 확정한다.

## 선행조건

- 프로젝트 설정과 `MswProvider`가 정상 동작한다.
- `src/mocks/handlers.ts`가 비어 있는 초기 상태다.
- 브라우저 저장소 외 실제 백엔드는 사용하지 않는다.

## Task 1.1. 공용 데이터 계약 정의

- feature-key: `mock-api`
- 예상 파일: `src/lib/pipeline.ts`

작업:

- [ ] `Stage`를 `서류검토 | 면접 | 처우협의 | 최종합격 | 불합격`으로 정의한다.
- [ ] `Applicant`에 `id`, `name`, `role`, `appliedAt`, `stage`만 정의한다.
- [ ] 컬럼 순서를 보장하는 `STAGES` 상수를 한 곳에 둔다.
- [ ] 날짜 원본은 정렬·표시에 사용할 수 있는 ISO 형식 문자열로 유지한다.
- [ ] 화면과 MSW가 동일한 타입과 단계 상수를 재사용하게 한다.

완료 확인:

- 단계명이나 필드가 UI와 mock 코드에 중복 하드코딩되지 않는다.
- 요구사항에 없는 연락처, 평가, 메모, 이력 필드를 추가하지 않는다.

## Task 1.2. 초기 지원자와 브라우저 저장소 구성

- feature-key: `mock-api`
- 예상 파일: `src/mocks/handlers.ts`, 필요 시 `src/mocks/data.ts`

작업:

- [ ] 직무와 단계가 분산된 지원자 데이터를 준비한다.
- [ ] 200건 성능 검증이 가능하도록 최소 200건을 생성하되 대형 fixture 파일을 직접 작성하지 않는다.
- [ ] 첫 조회는 초기 데이터를 사용하고 이후에는 브라우저 저장소의 성공 상태를 사용한다.
- [ ] 저장소 키를 한 곳에 정의한다.
- [ ] 저장소 값이 없거나 해석할 수 없으면 초기 데이터로 안전하게 복구한다.
- [ ] 실패한 단계 변경은 브라우저 저장소에 쓰지 않는다.

구현 기준:

- 단순 반복 데이터는 작은 seed 목록과 표준 배열 메서드로 생성한다.
- 별도 데이터 생성 라이브러리나 저장소 추상화 계층은 만들지 않는다.

완료 확인:

- 200건 이상 데이터가 같은 `Applicant` 계약을 만족한다.
- 페이지를 새로고침해도 마지막 성공 저장 결과가 초기화되지 않는다.

## Task 1.3. MSW 핸들러 구현

- feature-key: `mock-api`
- 예상 파일: `src/mocks/handlers.ts`

작업:

- [ ] `GET /api/applicants`가 `{ applicants }`를 반환한다.
- [ ] `PATCH /api/applicants/:id/stage`가 `{ stage }`를 받아 변경된 지원자를 반환한다.
- [ ] 모든 요청에 `200~800ms` 범위의 지연을 적용한다.
- [ ] 모든 요청에 약 `15%` 실패 확률을 적용한다.
- [ ] 존재하지 않는 지원자는 `404`, 허용되지 않은 단계는 `400`으로 응답한다.
- [ ] 성공한 PATCH만 메모리 상태와 브라우저 저장소에 반영한다.
- [ ] 오류 응답은 화면이 성공 응답과 구분할 수 있는 HTTP 상태를 사용한다.

완료 확인:

- GET 성공·실패가 모두 발생할 수 있다.
- PATCH 성공 시 응답과 저장 값의 단계가 같다.
- PATCH 실패 시 기존 저장 값이 유지된다.
