# Issue #8. 지원자 1,000건 독립 성능 검증 시나리오

[GitHub Issue #8](https://github.com/icecokel/worxphere-test/issues/8) · [Phase 6 계획](phase-6-should-improvements.md#task-65-1000건-성능-확인과-최소-개선) · [Should 요구사항](../requirements.md#5-도전-요구사항-should)

## 목적

지원자 1,000건에서 이름 검색, 다중 직무 필터와 컬럼별 추가 페이지 로드를 각각 측정한다. 실제 API 지연과 클라이언트 처리 시간을 분리하고, 재현 가능한 병목이 확인될 때만 현재 의존성으로 최소 개선한다.

feature-key는 `pipeline-performance`를 사용한다.

## 범위

- 데스크톱 Chromium의 `1024×768`, `1440×900`
- 이름 검색과 다중 직무 필터
- 다섯 컬럼의 독립 스크롤과 100건 단위 추가 페이지 로드
- 페이지 로드 중 검색 입력과 다른 컬럼 스크롤의 응답성
- API 요청 시간, 클라이언트 반영 시간과 Long Task

다음 항목은 측정으로 병목이 확인되기 전에는 진행하지 않는다.

- 보드 소스 코드 변경
- 1,000건 전체 선로딩
- 가상화 라이브러리나 별도 성능 계층 추가

## 공통 준비

1. 관련 없는 작업 트리 변경과 브라우저 생성물을 분리한다.
2. 측정 대상 커밋과 Chromium 버전을 기록한다.
3. `pnpm build` 후 `pnpm exec next start -H 127.0.0.1 -p 35555`로 프로덕션 모드를 실행한다.
4. CPU와 네트워크 제한을 적용하지 않는다.
5. `localStorage`의 `worxphere.applicants.v4`를 삭제하고 새로고침한다.
6. 검색어가 비어 있고 네 직무가 모두 선택된 상태에서 초기 조회를 완료한다.
7. 아래 초기 인원수와 최초 표시 카드 수를 확인한다.

| 컬럼 | 전체 인원 | 최초 표시 |
| --- | ---: | ---: |
| 서류검토 | 320 | 100 |
| 면접 | 120 | 100 |
| 처우협의 | 30 | 30 |
| 최종합격 | 50 | 50 |
| 불합격 | 480 | 100 |
| 합계 | 1,000 | 380 |

각 시나리오는 화면 크기별로 성공 응답 기준 3회 실행한다. mock API의 의도된 임의 `500`은 발생 횟수와 복구 여부를 별도로 기록하고 해당 회차를 성능 표본에서 제외한 뒤 다시 실행한다.

## 측정 방법

모든 시각은 브라우저의 단조 시계인 `performance.now()`를 사용한다. 동작 직전에 Resource Timing 버퍼와 Long Task 기록을 비우고 측정을 시작한다.

| 측정값 | 정의 |
| --- | --- |
| 동작 시작 | 검색 입력 또는 필터·스크롤 동작 직전 시각 |
| 요청 시작 지연 | 첫 `/api/applicants` GET 시작 시각 - 동작 시작 |
| API 시간 | 각 GET의 `responseEnd - startTime`; 회차별 최댓값도 기록 |
| 화면 안정 | 기대 카드·인원수가 반영되고 로딩 표시가 사라진 뒤 두 번째 `requestAnimationFrame` 시각 |
| 클라이언트 반영 | 화면 안정 시각 - 마지막 GET `responseEnd` |
| 전체 완료 | 화면 안정 시각 - 동작 시작 |
| Long Task | 동작 시작부터 화면 안정까지 발생한 `50ms` 이상 메인 스레드 작업 |

검색·필터 회차는 다섯 단계의 1페이지 GET이 모두 성공하고 화면이 안정돼야 완료한다. 페이지네이션 회차는 대상 컬럼의 카드 증가와 로딩 종료를 화면 안정 조건으로 사용한다.

## PERF-01. 이름 검색

### 선행 상태

- 필터가 없는 초기 1페이지 상태
- 검색 입력이 활성화된 상태

### 절차

1. 측정을 시작하고 검색 입력에 `김민준`을 한 번의 입력 이벤트로 설정한다.
2. `name=김민준`, `page=1`인 단계별 GET 5건을 수집한다.
3. 화면 안정 시각과 컬럼별 인원수, 표시된 모든 카드 이름을 기록한다.
4. 검색어를 지우고 초기 1페이지 상태가 복구될 때까지 기다린다.
5. 같은 절차를 총 3회 반복한다.

### 기대 결과

- 서류검토 2명, 불합격 2명이며 나머지 컬럼은 0명이다.
- 표시된 네 카드의 이름은 모두 `김민준`이다.
- 검색 중 입력값이 유실되지 않고 새 필터 요청이 시작된다.
- 전체 완료, 각 API 시간과 클라이언트 반영 시간이 분리돼 기록된다.

## PERF-02. 다중 직무 필터

### 선행 상태

- 검색어가 비어 있고 네 직무가 모두 선택된 초기 1페이지 상태

### 절차

1. `프로덕트 디자이너` 선택을 해제하고 화면이 안정될 때까지 기다린다.
2. 측정을 시작하고 `프로덕트 매니저` 선택을 해제한다.
3. `프론트엔드 개발자`와 `백엔드 개발자`가 반복 `role` 파라미터로 전달된 단계별 GET 5건을 수집한다.
4. 화면 안정 시각, 컬럼별 인원수와 표시 카드의 직무를 기록한다.
5. 네 직무 전체 선택 상태로 복구하고 같은 절차를 총 3회 반복한다.

### 기대 결과

| 컬럼 | 필터 결과 | 최초 표시 |
| --- | ---: | ---: |
| 서류검토 | 160 | 100 |
| 면접 | 60 | 60 |
| 처우협의 | 16 | 16 |
| 최종합격 | 24 | 24 |
| 불합격 | 240 | 100 |
| 합계 | 500 | 300 |

- 표시된 카드의 직무는 프론트엔드 또는 백엔드 개발자뿐이다.
- 전체 완료, 각 API 시간과 클라이언트 반영 시간이 분리돼 기록된다.

## PERF-03. 컬럼별 연속 스크롤

### 선행 상태

- 필터가 없는 초기 1페이지 상태

### 절차

1. 서류검토 컬럼을 하단까지 스크롤하고 로딩 종료를 기다리는 동작을 `hasMore=false`가 될 때까지 반복한다.
2. 면접, 처우협의, 최종합격, 불합격 컬럼에도 같은 절차를 적용한다.
3. 추가 GET마다 페이지 번호, API 시간, 클라이언트 반영 시간과 카드 증가량을 기록한다.
4. 마지막 페이지 이후 다시 하단으로 스크롤해 불필요한 GET이 발생하지 않는지 확인한다.

### 기대 결과

| 컬럼 | 카드 증가 순서 | 추가 GET |
| --- | --- | ---: |
| 서류검토 | `100 → 200 → 300 → 320` | 3 |
| 면접 | `100 → 120` | 1 |
| 처우협의 | `30` | 0 |
| 최종합격 | `50` | 0 |
| 불합격 | `100 → 200 → 300 → 400 → 480` | 4 |

- 추가 GET은 총 8건이며 최종 표시 카드는 1,000건이다.
- 각 요청은 대상 컬럼의 다음 페이지만 추가하고 다른 컬럼의 카드 수를 바꾸지 않는다.
- 마지막 페이지 뒤에는 같은 컬럼의 후속 요청이 발생하지 않는다.

## PERF-04. 추가 페이지 로드 중 응답성

### A. 다른 컬럼 스크롤

1. 필터가 없는 초기 1페이지 상태로 복구한다.
2. 불합격 컬럼의 2페이지 요청을 시작한다.
3. 해당 응답을 기다리지 않고 서류검토 컬럼을 하단으로 스크롤한다.
4. 두 컬럼의 요청·응답과 카드 증가 시각을 기록한다.

기대 결과:

- 불합격과 서류검토의 2페이지 GET이 각각 한 번 발생한다.
- 한 컬럼의 로딩이 다른 컬럼 스크롤이나 페이지 요청을 차단하지 않는다.
- 두 컬럼은 각각 `100 → 200`으로 증가한다.

### B. 이름 입력

1. 필터가 없는 초기 1페이지 상태로 다시 복구한다.
2. 불합격 컬럼의 2페이지 요청을 시작하고 즉시 검색 입력에 `김민준`을 설정한다.
3. 입력값 반영, 기존 페이지 요청 취소와 새 단계별 검색 요청 시작을 기록한다.
4. 검색 결과가 안정될 때까지 기다린다.

기대 결과:

- 검색 입력값이 유실되지 않고 새 검색 요청이 시작된다.
- 필터 변경 전 페이지 요청은 이전 결과를 뒤늦게 추가하지 않는다.
- 최종 화면은 `PERF-01`과 같은 서류검토 2명, 불합격 2명이다.
- 취소된 요청은 API 실패나 성능 표본으로 계산하지 않고 별도로 기록한다.

## 병목 판정

정확성 조건을 모두 통과한 뒤 다음 중 하나가 같은 동작의 3회 중 2회 이상 재현되면 클라이언트 병목 후보로 판단한다.

- 클라이언트 반영 구간에 Long Task가 발생한다.
- 입력값, 다른 컬럼 스크롤 또는 카드 증가가 기대한 화면 갱신에서 누락된다.
- 클라이언트 반영 시간이 해당 회차의 가장 느린 API 시간보다 길다.

병목 후보가 없으면 현재 100건 페이지네이션을 유지하고 가상화를 생략한 근거를 기록한다. 후보가 있으면 해당 구간의 브라우저 trace로 원인을 확인하고, 현재 React·브라우저 기능으로 가능한 가장 작은 변경만 적용한 뒤 같은 시나리오를 다시 실행한다.

### 판정

- 이름 검색의 클라이언트 반영은 `43.8~51.0ms`, 다중 직무 필터는 `50.5~82.2ms`였다.
- 추가 페이지의 회차별 최대 클라이언트 반영은 `36.5~54.8ms`였다.
- 다른 컬럼 동시 스크롤과 페이지 로드 중 검색 입력은 모든 성공 회차에서 반영됐고, 기존 페이지 요청은 모두 `request → failed`로 취소됐다.
- 모든 측정 구간의 Long Task는 `0건`이며, 클라이언트 반영 시간이 같은 회차의 최대 API 시간보다 길었던 회차도 없다.
- 재현 가능한 클라이언트 병목이 없어 현재 100건 페이지네이션을 유지하고 가상화를 생략한다.

임의 `500`으로 제외한 측정 요청은 `1024×768`에서 9건, `1440×900`에서 19건이었다. 현재 화면에 남은 콘솔 오류 2건도 초기 조회의 의도된 `500` 응답이며 예상하지 못한 애플리케이션 오류는 없었다.
