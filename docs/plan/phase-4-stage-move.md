# Phase 4. 상세 패널 단계 변경과 낙관적 업데이트

[전체 계획](README.md) · 기준: [단계 변경 흐름](../wireframe.md#5-단계-변경과-저장-흐름)

## 목표

지원자 상세 패널에서 현재 상태에 맞는 액션을 확인한 뒤 저장한다. `다음 채용 단계`와 `불합격 처리`를 분리하고, API 응답 전 화면 반영·성공 저장·실패 롤백을 하나의 일관된 흐름으로 구현한다.

## 완료 기준

- [x] 상세 패널에서 현재 단계에 맞는 다음 채용 단계 액션만 확인할 수 있다.
- [x] 불합격 처리는 별도 섹션에서 `서류검토`, `면접`, `처우협의`에만 제공한다.
- [x] 중간 단계 건너뛰기와 이전 단계 변경을 막고, 확인을 취소하면 상태나 API 요청이 발생하지 않는다.
- [x] 확인 후 카드·컬럼 인원수·상세 패널을 즉시 갱신하고 PATCH 요청을 한 번 보낸다.
- [x] 저장 성공은 새로고침 후에도 유지되고, 저장 중에는 같은 지원자의 중복 변경을 막는다.
- [x] 저장 실패는 카드·인원수·상세 패널을 이전 상태로 복구하고 오류를 알린다.
- [x] Phase 검증과 `PROMPTS.md`의 `[stage-move]` 기록이 완료됐다.

## 선행조건

- Phase 3까지의 보드, 필터, 상세 패널이 완료됐다.
- Phase 1의 PATCH API가 성공과 실패를 모두 반환한다.
- 지원자 원본 상태가 한 곳에서 관리된다.

## Task 4.1. 상세 패널의 명시적 단계 변경

- feature-key: `stage-move`
- 예상 파일: `src/components/pipeline-board.tsx`

작업:

- [x] 카드 선택은 상세 패널 열기만 수행하고 드래그앤드롭 동작을 제공하지 않는다.
- [x] 단계 선택 UI 없이 현재 상태에 맞는 다음 채용 단계 버튼을 표시한다.
- [x] 정규 전이는 `서류검토 → 면접 → 처우협의 → 최종합격`의 다음 단계만 허용한다.
- [x] 불합격 처리 섹션은 `서류검토`, `면접`, `처우협의`에서만 별도 버튼으로 표시한다.
- [x] 다음 단계가 없거나 이미 불합격인 상태는 해당 액션을 비활성화하거나 안내한다.
- [x] 액션 버튼을 누르면 shadcn/ui 확인 모달에서 지원자 이름, 이전 단계, 대상 단계와 알림 가능성을 확인한 뒤 확정한다.
- [x] 확인을 취소하면 화면 상태와 API 요청을 모두 유지한다.
- [x] 실제 알림 발송은 요구사항의 범위 밖이므로 구현하지 않는다.

## Task 4.2. 낙관적 업데이트와 저장

- feature-key: `stage-move`

작업:

- [x] 확인 후 해당 지원자의 `stage`를 화면 상태에서 즉시 변경한다.
- [x] 변경 직후 `PATCH /api/applicants/:id/stage`를 호출한다.
- [x] 저장 중인 지원자 ID를 최소 상태로 관리한다.
- [x] 저장 중에는 두 섹션의 액션 버튼을 비활성화하고 `변경 중…`을 표시한다.
- [x] 성공 응답 후 대상 컬럼 위치를 유지하고 저장 중 표시를 제거한다.
- [x] 상세 패널은 같은 원본 상태에서 현재 단계를 즉시 반영한다.
- [x] 검색·필터 결과와 컬럼 인원수도 낙관적 상태를 기준으로 갱신한다.

## Task 4.3. 실패 롤백과 알림

- feature-key: `stage-move`

작업:

- [x] 요청 전 단계 값을 롤백에 필요한 최소 정보로 보관한다.
- [x] PATCH 실패 시 해당 지원자의 단계만 이전 값으로 복구한다.
- [x] 원본 배열 순서를 유지해 이전 컬럼 내 위치도 자연스럽게 복구한다.
- [x] `단계 변경에 실패했습니다. 다시 시도해 주세요.`를 `role="alert"`로 표시한다.
- [x] 실패 알림은 사용자가 닫을 수 있고 일정 시간 뒤 제거한다.
- [x] 실패 후 상세 패널에서 다시 변경을 시도할 수 있게 한다.
- [x] 실패 응답은 브라우저 저장소와 성공 상태를 오염시키지 않는다.

## 커밋

```text
fix(stage-move): 단계 변경을 상세 패널 액션으로 전환
```

같은 지원자의 다중 요청 순서 제어와 실행 취소는 Should이므로 이 Phase에 추가하지 않는다. 실제 알림 발송은 범위 밖으로 유지하며, 이 화면에서는 확정 전 영향 가능성을 고지한다.
