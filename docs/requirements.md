# 채용 파이프라인 보드 요구사항

## 1. 문서 목적

이 문서는 과제 구현의 판단 기준을 정의한다. 명시된 요구사항을 우선하며, 요구되지 않은 기능으로 범위를 확장하지 않는다.

## 2. 프로젝트 목표

채용 담당자가 지원자의 현재 채용 단계를 한눈에 파악하고, 지원자를 단계 간에 안전하게 이동·관리할 수 있는 채용 파이프라인 보드를 만든다.

핵심 성공 기준은 다음과 같다.

- 지원자의 현재 단계를 빠르게 파악할 수 있다.
- 단계 이동 결과가 저장되고 새로고침 후에도 유지된다.
- 저장 실패가 발생해도 화면과 데이터가 일관된 상태로 복구된다.
- 지원자가 많아도 필요한 지원자를 검색하고 분류할 수 있다.

## 3. 사용자와 배경

### 사용자

주 사용자는 여러 지원자의 채용 진행 상태를 관리하는 **채용 담당자**다.

### 배경

채용 담당자는 지원자를 다음 단계로 구분해 관리한다.

`서류검토 → 면접 → 처우협의 → 최종합격`

`불합격`은 `서류검토`, `면접`, `처우협의`에서만 처리할 수 있는 종료 상태다. `최종합격`과 `불합격`은 모두 변경할 수 없는 종료 상태다.

지원자가 많아지면 현재 상태를 파악하거나 변경하기 어려워진다. 사용자는 단계별 지원자 목록을 확인하고, 지원자를 적절한 단계로 이동하며, 필요한 지원자를 검색하거나 상세 정보를 확인할 수 있어야 한다.

## 4. 필수 요구사항 (Must)

### 보드와 지원자 카드

- 채용 단계를 각각 하나의 컬럼으로 표시한다.
- 지원자를 현재 단계의 컬럼에 카드로 표시한다.
- 카드에 이름, 직무, 지원일, 현재 단계를 표시한다.

### 단계 이동

- 사용자는 지원자를 다른 단계로 이동할 수 있다.
- 이동 방식은 지원자 상세 패널의 명시적 액션 버튼으로 한다.
- 정규 단계 변경은 `서류검토 → 면접 → 처우협의 → 최종합격`의 바로 다음 단계로만 진행하며, 중간 단계 건너뛰기와 이전 단계 변경을 허용하지 않는다.
- 불합격 처리는 `서류검토`, `면접`, `처우협의`에서만 별도 액션으로 할 수 있으며, `최종합격`과 이미 불합격인 지원자는 변경하지 않는다.
- mock API는 최종합격 지원자를 불합격으로 변경하려는 요청에 `400` 응답을 반환한다.
- 단계 변경은 지원자에게 영향을 주고 알림이 이어질 수 있으므로, shadcn/ui 확인 모달에서 변경 대상과 단계를 확인한 뒤 확정한다.
- 이동 결과를 mock API에 저장한다.
- 저장된 단계는 새로고침 후에도 유지되어야 한다.

### 낙관적 업데이트

- 단계 이동 시 API 응답을 기다리지 않고 화면에 먼저 반영한다.
- API 요청이 실패하면 이동 전 단계로 복구한다.
- 실패 사실을 사용자에게 알린다.

### 검색과 필터

- 이름으로 지원자를 검색할 수 있다.
- 직무별로 지원자를 필터링할 수 있다.
- 지원자가 200건 이상이어도 다음 성능 기준을 만족해야 한다.
  - 프로덕션 모드의 데스크톱 Chromium `1024×768`, `1440×900`에서 CPU·네트워크 제한 없이 성공 응답 기준 3회 측정한다. 1,000건 측정은 200건 이상 Must의 검증을 겸할 수 있다.
  - 이름·직무 조건을 바꾼 뒤 첫 목록 요청이 `100ms` 안에 시작되고 입력값과 선택 상태가 유실되지 않아야 한다.
  - 마지막 목록 응답 뒤 카드·인원수·로딩 상태가 `100ms` 안에 안정되고 클라이언트 반영 구간에 `50ms` 이상 Long Task가 없어야 한다.
  - 1,000건 Should에서도 위 기준을 유지하고, 추가 페이지를 불러오는 동안 검색 입력과 다른 컬럼 스크롤이 차단되지 않아야 한다.

### 상세 보기

- 지원자 카드를 선택하면 상세 정보를 확인할 수 있다.
- 상세 정보는 사이드 패널 또는 모달로 제공한다.

### 화면 상태

- 데이터 로딩 상태를 표시한다.
- 데이터 요청 실패 상태를 표시한다.
- 표시할 지원자가 없는 빈 상태를 표시한다.

## 5. 도전 요구사항 (Should)

필수 요구사항을 완료한 후 남은 시간에 선택적으로 구현한다.

- 같은 카드를 빠르게 연속 이동해도 데이터가 깨지지 않도록 경쟁 상태를 처리한다.
- 지원자 1,000건 기준으로 스크롤과 필터가 부드럽게 동작하도록 한다.
- 최근 단계 이동을 되돌릴 수 있도록 한다.
- 낙관적 업데이트와 롤백 등 핵심 로직을 테스트한다.
- 키보드만으로 단계 이동과 상세 열람이 가능하도록 한다.

## 6. 기술 및 데이터 제약

- React 또는 Next.js를 사용할 수 있으며 상태 관리와 스타일링 방식은 자유다.
- 실제 백엔드 대신 mock API 또는 로컬 mock 서버를 사용한다.
- API의 채용 단계 값은 영문 enum 코드로 송수신하고 한글 단계명은 화면 표시에만 사용한다.
- API에 200~800ms의 네트워크 지연을 적용한다.
- API 요청은 약 15% 확률로 실패하도록 한다.
- 외부 UI 라이브러리를 사용할 수 있다.
- 핵심 상태 로직을 대신하는 라이브러리를 사용하면 선택 이유를 문서에 남긴다.

## 7. 작업 및 제출 요구사항

- AI 도구를 반드시 사용한다.
- 하나의 기능을 하나의 커밋으로 기록한다.
- 커밋을 squash하거나 force-push로 정리하지 않는다.
- `PROMPTS.md`에 기능별 프롬프트와 AI 출력에 대한 실제 리뷰·검증 내용을 남긴다.
- `DECISIONS.md`에 주요 설계 결정, AI 제안의 채택·기각 이유, 완료하지 못한 기능과 이유를 남긴다.
- `README.md`에 설치·실행 방법, 기술 스택, mock API 방식을 명시한다.
- 동작하는 코드와 문서를 공개 GitHub 저장소로 제출한다.

## 8. 범위 밖

다음 기능은 요구사항에 없으므로 구현 범위에 포함하지 않는다.

- 지원자 등록·수정·삭제
- 채용 공고 관리
- 면접 일정 및 평가 관리
- 사용자 인증과 권한 관리
- 알림과 메시지 발송
- 실제 백엔드 및 운영 배포 환경

## 9. 구현 원칙

- Must를 Should보다 우선한다.
- 요구사항이 모호하면 가장 작은 호환 가능한 해석을 선택하고 `DECISIONS.md`에 가정을 기록한다.
- 기능 수보다 동작의 정확성, 실패 처리, 검증 가능한 작업 기록을 우선한다.
